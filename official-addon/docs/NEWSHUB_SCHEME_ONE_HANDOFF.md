# NewsHub 方案一：Dart 业务桥接入任务书与前置阻断

## 已确认的决策

用户选择方案一：在可修改、可构建的官方 Dart 业务层增加入口，调用原稿件保存及读取逻辑。不是点击官方导入后替换文件选择结果，也不是只新增 native MethodChannel 调用。

## 裁决

**方案一目前缺少接入位置，不能开始真实业务桥代码实施。** 这是前置材料阻断，不是“等用户手动点导入”。不会写只有native端的空壳、返回假的docId或把mock测试作为官方入库完成。

也不在本次方案一下自动恢复旧AOT逆向路线；若改走二进制重建／注入，需要用户另行选择方案二和相应验证范围。

## 最少需要的材料（二选一）

### A. 对应目标的官方可构建工程

- 有权使用和修改、对应官方iOS1.0.5（201）或可明确映射该行为的Flutter/Dart源码revision。
- 依赖锁文件、生成步骤和必要构建配置；能先重建未经业务修改的基线。
- 官方稿件导入／解析、保存、按ID读取、列表刷新代码及依赖注入／状态容器的初始化位置。
- 与现有引擎/isolate共同运行并注册新增桥入口的方法，而非另起一个不共享原业务状态的main。

无需提供账号、签名私钥、模型密钥或私人稿件。厂商可只提供最小可验证扩展模块，不必交出整个业务仓库。

### B. 厂商支持的业务扩展 Interface

- 原Dart层真实处理入口／注册位置和兼容1.0.5（201）的约束。
- 标题、正文或受控文件输入的类型、UTF-8／大小约束、返回错误与异步完成语义。
- 返回稳定官方docId，以及按ID读取并核验正文、查询未知创建结果的方法。
- 引擎／线程／isolate与对象生命周期要求，启动和恢复后可用性。

只有channel字符串、native头文件、AOT地址或“传给眼镜成功”都不满足材料条件。

## 前置条件满足后的实施顺序（计划，不是已存在的 Interface）

1. 固定对应1.0.5（201）可重建官方基线，验证未修改稿库读写行为。
2. 在原业务初始化完成处注册小型导入／查询入口；Implementation调用官方现有解析和保存逻辑，不维护影子稿库、不直写官方DB。
3. 先验证一篇公开fixture：创建→真实docId→按ID读回标题正文→官方列表可见→重启后仍可查。
4. 再接NewsHub源标识／内容指纹与状态机，消化明确失败、超时、取消、结果未知和重复请求。
5. 最后接多来源、时间配置及重试，独立构建与真机验收后才交付新IPA。

不会仅根据客户端requestId声称官方幂等已建立；业务端必须有可验证的去重／查询契约，否则未知结果停止自动再创建。

## 验收门槛

- 零官方导入按钮点击、零页面跳转；无隐藏编辑器替代。
- 一篇／多篇／各来源独立稿件，非空无损UTF-8，实际TXT <=1,000,000 bytes保守门禁。
- 官方保存结果包含稳定ID，独立按ID读取核对标题与正文；native返回不计官方保存成功。
- 官方列表与重启持久性核验，取消／错误不伪报成功。
- 同请求重发、超时／崩溃后未知结果，先核验后重试，不重复生成。
- 明确保存成功后才能按已验证消费完成规则清理临时文件，不能在文件选择回调返回就删除。
- 原TinyFish和配置兼容，不混1.0.6版源码／ABI／固件；不开启OTA或自动刷写。
